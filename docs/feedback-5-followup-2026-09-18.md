## 2. 批次A：输入选择与输出路由 / Batch A: input selection and output routing

涉及场景模型/迁移、`resolved_audio_inputs()`、`AudioWorkspace` 和 OBS 音频配置。

### 必须修复

1. 显式 `audioInputs: []` 表示关闭该来源音频，不能回退到 `audioTrack-1`。解析时区分缺省和空列表；采用内部 presence 标记或 optional 表示，不要求客户端增加字段。
2. `audioTrack` 保持输出总线1～6的含义。UI选择输入轨不能再用 `input.track+1` 改写它。旧场景缺少输入选择时按第一条可用音频输入迁移，保留原输出总线。
3. 无音轨来源不能因迁移自动创建 `a:0` 混音任务，导致视频输入一起失败；确认无音轨时继续正常视频播放。未知探测状态与确认无音轨分开处理。
4. OBS输出总线和Program监听路由分别遵循既有契约，不用统一 `1U` 掩盖输出路由设置。保证输入选轨不影响用户配置的输出总线。
5. 已有v6显式选择保持原值，不根据猜测批量修正用户配置。无法区分用户选择和历史错误迁移时说明限制。

### 完成条件

- v5输出轨2/6且只有一条输入音轨，迁移后仍正确播放并保留输出配置。
- 全部取消选择后真正无声，保存重载仍无声，再选择时恢复。
- 选择输入序号6或7时不产生 `audioTrack>6` 校验错误。
- 无音轨摄像头保存、迁移、重启后视频正常，无无效混音进程。
- C++测试覆盖解析后运行时解析结果；仅断言JSON空数组被读入不够。前端测试覆盖保存内容和重载。

## 3. 批次B：混音源更新与错误处理 / Batch B: mix-source updates and error handling

现状：创建混音路径发生在复用判断之前。显式音轨配置每次重建媒体源；新配置为空时仍可能复用旧混音源，却未共享旧 `audio_mix` 守卫。混音路径创建失败会继续走原始输入。

实现要求：

- 先计算配置等价性，再决定是否创建路由。布局、名称等不影响媒体的变化复用当前源和路由守卫；来源master音量/静音在OBS端更新。
- 选轨、逐轨增益/静音/偏移等改变时，准备新混音路由并验证有效，再切换；旧源停止消费后才删除旧路由。
- 从混音切到空列表或旧默认输入必须明确切换路径，不能复用仍指向旧mix地址的源。修复新旧两侧配置比较，不只检查新配置是否为空。
- 创建/验证失败时保留现有节目，返回来源级错误；禁止成功保存后悄悄改播默认轨。
- 网关优先读取已有共享RTSP路径，核对不会为每轨重复连接摄像头。路由与进程需有可验证的所有者及回收时机。

完成条件：连续20次只改布局或重复保存，mix路径、拉流和转码进程数量稳定，视频不中断；多轨→单轨→空列表→恢复、切换非默认轨均正确；准备失败不破坏旧节目；删除来源和退出后无本次创建的路径残留。保留首轨静音和增益回归，确保生命周期修复没有重新引入该缺陷。

## 4. 批次C：有符号同步偏移 / Batch C: signed synchronization offsets

模型和UI允许±10000ms，但脚本目前只接受非负数，此项仍未完成。

保留原有外部范围。对选中轨道偏移 `d_i`，计算 `B=max(0,-min(d_i))`：各音频延迟 `B+d_i`，对应视频增加 `B` 延迟，从而保持音视频相对偏移。内部延迟最大20000ms，来源级同步独立应用一次。使用实际帧/音频时间和输出节奏验证；仅改变PTS标签不等于真正延迟播放。实现应保持有界缓冲并报告新增端到端延迟。

以带闪光和同步音脉冲的素材验证零、正、负、混合正负、范围边界以及保存重载。不要用“检测到了两种频率”代替同步正确。若该实现确实受现有媒体架构限制，提交可复现限制和受影响范围，禁止静默归零或声称全功能完成。

已有 `index/stream_index` 区分保留。另用视频绝对索引0、音频绝对索引1/2的源验证UI→API→脚本实际选择音频序号0/1。

### 验收顺序与门槛

软件降级测试单列，不能替代1080p验收。资源占用注明多核CPU口径，并分别记录来源转码、OBS渲染/编码、浏览器解码。Docker/vGPU和跨设备音视频组合继续留到后续。
