## 1. 本轮任务：持续推进全部要求 / Continue toward all acceptance requirements

用户要求继续实际开发和验证，尽量完成反馈5全部约定要求。本轮不是再次写计划，也不是只修一个小问题后结束。

按“取未完成项→实现→针对性测试→修复失败→提交→继续下一项”循环执行。完成一次提交、一个批次、编译成功或一个测试通过，均是中间节点；只要有安全、相关、可执行的后续工作，就继续，不需要每一步等待用户说“继续”。

允许长时间工作；不以5分钟、一个提交或一个会话摘要作为结束点。工作时长由剩余任务和真实测试决定，不为凑时长空等、不反复运行已经通过且不受后续改动影响的测试。两种播放模式的正式长稳各需要至少30分钟，应留足修复与测试时间。

每约60秒提供简短进度，说明新的发现、正在处理的事项或测试进展。进度更新不是最终交接。长稳期间使用有界轮询保持可响应，测试由可靠进程执行，不能因单次工具等待返回就认为测试结束。

## 2. 一次启动后的执行顺序 / Work sequence

1. 读取9月18日计划和当前验收报告，核查实际HEAD、工作区及运行进程；建立六项反馈的完成清单，标注证据SHA。不要重新发现已明确的全部历史问题。
2. 完成批次A：空选轨、旧场景迁移、输入轨/输出总线分离及无音轨视频保护。
3. 完成批次B：相同配置复用、混音路径所有权、配置变化先备后切及失败保留旧节目。保留已完成的重复增益修复。
4. 完成批次C：逐轨正负偏移与视听同步验证。音频序号解析已区分 `index/stream_index`，核验端到端映射即可。
5. 完成批次D的基础设施：Windows `-Soak` 转发、可重复音频回归、持续采样和证据输出脚本。
6. 在当前代码上做短时端到端测试和GPU能力归因；通过后固定待验收代码提交，启动正式浏览器长稳。
7. Direct/Hybrid五路浏览器30分钟，随后Composite原始1920×1080及原目标帧率30分钟。两种负载顺序测试，避免同时竞争资源污染结果。
8. 独立进行单路断开恢复、切场景、保存重载、声音启停、拓扑切换测试；修复发现的问题，并重跑受影响的验收。
9. 检查全部六项门槛，修订报告，将过时结论移入历史附录；仅当下述停止条件满足时最终交接。

互不干扰的静态检查、文档整理可以并行；不要在长稳期间修改运行配置、热更新被测代码、重启被测进程或执行其他重负载实验。

## 3. 六项要求的关闭标准 / Closure criteria for all six items

| 反馈 | 最终需要的行为与证据 |
|---|---|
| F5-01 画面填充 | 默认拉伸，完整显示次之，裁剪需用户主动选择；1/2/4/5/9/16路、两大三小布局无意外空槽；四角标记完整，检测框随同一几何变换；Direct和Composite一致，手动配置保留 |
| F5-02 干净画面 | 诊断按钮及默认状态放在画布外；关闭可选叠加后无诊断遮挡；来源状态能定位问题；全屏、窗口缩放和键盘操作通过 |
| F5-03 硬件加速 | 分别报告网关解码/编码、OBS编码/渲染、浏览器解码；实际运行证据与UI吻合；可用硬件路径尝试启用并验证，失败有明确原因及回退，不能用FFmpeg小样代替OBS验证 |
| F5-04 本地合成 | 标准Windows启动入口能检查、构建、运行Composite；五路来源经OBS与MediaMTX到实际应用Program播放器持续出图；未启用/缺依赖/发布失败有可操作提示 |
| F5-05 音频管理 | 无音轨隐藏控制；未知与静音不误判；单轨/多轨选择、空列表、增益、静音、输出总线、正负偏移、保存重载都正确；逐轨/合并电平有真实数据；路由切换和释放无误 |
| F5-06 播放稳定 | 五路Direct/Hybrid和Composite浏览器各30分钟；逐源帧推进、首帧、帧率、停滞、恢复、CPU/GPU和资源回收都有绑定代码版本的证据 |

性能门槛沿用上一份计划：首帧≤20秒，已就绪路由重开≤8秒，实际解码帧率≥配置目标90%，正常运行无超过3秒的非预期帧停滞；单路恢复后15秒内出图，其余四路不被一起重建。低功耗按明确的目标帧率单列。

长稳从全部被测流达到就绪开始计时。真实产品页面必须纳入端到端测试；直接访问MediaMTX可用于定位，但不能代替应用的授权、计划激活、播放器和UI路径。

历史降负载服务端30分钟仅作为已有证据保留；41帧/20秒证明持续解码，但不满足5fps目标的90%门槛。发布总字节持续增长也不能证明五路各自没有冻结。

Docker/vGPU实机验收和跨设备音视频组合继续按用户已确认范围留到后续，不因“持续执行”扩大任务。

## 4. 失败和环境限制的处理 / Handling failures and environment limits

- 同一症状复现两次且没有新证据时，先添加阶段日志、捕获退出码或缩小实验。次数限制的是盲目重试，不是整个任务。
- 一项GPU验收受阻时，继续完成独立的音频修复、迁移、UI、启动器和验收工具；单项受阻不能结束其他可执行工作。
- 重新探测当前环境。此前已发现WSLg环境变量、目录和 `/dev/dxg`，需要检查真实图形连接、实际renderer及插件注册；不能直接沿用“环境没有WSLg”的报告结论。
- 尝试Windows Chrome连接WSL后端，将浏览器能力与OBS运行环境分开定位。缺少gdb或ss不自动等于无法继续；先使用现有日志、退出状态及系统信息。
- 构建依赖优先在项目/用户缓存中按固定版本准备。涉及必须的新权限或用户选择时说明具体需要，同时继续不依赖该权限的工作。
- 性能不达标时先定位渲染、编码、来源拉流或浏览器解码瓶颈；保持原始验收规格。降负载实验只用于诊断，不能改小验收目标后宣布通过。
- 不使用全局pkill、不重启整个WSL或系统来回避诊断；清理仅限本次拥有的进程/路由，原始摄像头配置与用户场景保留。

## 6. 提交和语言要求 / Commit and language requirements

**开发过程、技术分析允许英文；每个commit的标题与正文、PR标题与description、最终变更与验收描述必须中英文双语。** 两种语言必须表达相同的测试结果及限制。

示例：

```text
fix(audio): 修复空选轨与输出总线混用 / Fix empty selections and output-bus confusion

中文：<具体问题、改变后的行为>
English: <The same problem and resulting behavior>
验证 / Validation: <实际执行的测试和结果>
限制 / Limitations: <仍待完成的验收>
```

按工作主题提交，每个提交后继续下一项，不因提交完成结束本轮。不改写旧历史，不自动push、发布或纳入无关未跟踪文件。测试证据注明实际被测提交，旧测试次数不能直接复制给新HEAD。

## 7. 允许最终交接的条件 / Conditions for final handoff

只在下列任一情况成立时结束本轮：

1. **完成**：所有本轮范围内的实现与验收门槛通过，报告无矛盾，证据可定位。
2. **确实需要外部介入**：独立可完成工作已经做完，余项需要当前无法获得的权限、设备、来源或用户决定；提供失败证据、已尝试的不同办法和最小所需操作。单纯尚未调查或测试耗时较长不属于此类。
3. **用户明确暂停/停止，或平台强制终止**：保存检查点，如实标记未完成。

最终交接以中文为主，并附对应英文说明。逐项列出通过、失败、待验收；列出相关提交、真实测试时长、证据位置和剩余限制。不要只回复“本轮修好了一个问题，是否继续”；还有可执行项时直接继续工作。
