## 2. 优先修复音频语义 / Correct audio semantics first

涉及 `core/src/obs_scene_runtime.cpp`、场景模型/迁移、`gateway/transcode-on-demand.sh` 和 `web/src/AudioWorkspace.tsx`。

### 2.1 重复增益和首轨静音 / Duplicate gain and first-track mute

现状：网关已经应用逐轨 gain/muted；`commit_prepared()` 又对整个混合结果调用 `drive(..., inputs.front())`。第一轨静音会令整个来源静音，第一轨增益会再次缩放所有轨。

修复：混音路径中逐轨增益、静音只在网关应用一次，OBS 仅应用来源 master volume、master mute 和来源级同步。直连旧路径单独处理，不能共用首轨增益逻辑。

回归：双频素材第一轨静音时第二轨仍可听；第一轨 gain=0.25、第二轨 gain=1 时后者不被整体衰减；来源总静音能关闭两轨。分别测网关输出和 Program 输出以定位增益层级。

### 2.2 混音路由复用与所有权 / Mix route reuse and ownership

现状：`create_source_entry()` 先创建新 mix 路径，随后可能进入旧源复用分支；复用返回值未复制 `audio_mix` 守卫，也未保证音轨参数一致。

修复：先计算有效配置再决定复用；只有输入端点、选轨、增益、静音、偏移及相关媒体配置均一致时复用混音结果，并共享旧路由守卫。配置变化时准备新路由，确认可用后切换，释放旧消费者后删除旧路由；准备失败保留当前播放。路由创建失败必须返回可诊断错误，不能默默播放默认音轨。

回归：相同场景重复保存、仅修改布局、单轨增益更新、双轨改单轨、切换非默认轨、准备失败及删除来源。检查声音正确、无无谓视频重连、路由数量有界、活动路由不被提前删除。

### 2.3 空列表、输入轨与输出轨 / Empty selection and track semantics

现状：`resolved_audio_inputs()` 把空列表回退到 `audioTrack-1`；迁移同样把输出轨误当输入轨。前端保存选轨时又用输入轨号改写 `audioTrack`。这与原计划“audioTrack 保留输出总线 1～6”冲突。

修复：明确区分字段缺省与显式 `audioInputs: []`。显式空列表表示不播放来源音频；缺省的旧场景采用第一条可用输入轨，保留原输出轨配置。前端选轨不改写 `audioTrack`。输出总线设置和 Program 使用的监听总线分别处理，保证预览声音与输出路由语义正确。

回归：输出轨为2或6、输入只有一条的 v5 场景；显式取消全部选轨；选择索引大于5的输入轨；保存和重载。不要全局重写已有 v6 用户配置：对于已保存的显式输入无法判定是否来自错误迁移时保留选择，并记录兼容限制。

### 2.4 偏移范围及索引映射 / Offset range and index mapping

现状：模型和界面接受 -10000～10000ms，混音脚本仅接受非负数；Profile 的媒体绝对索引与 FFmpeg `a:N` 的音频序号还需核对。

保留已有 -10000～10000ms 契约并实现完整语义：以 B=max(0,-min(各选中轨偏移)) 归一化，音频各轨延迟为 B+自身偏移，视频增加 B 的对应延迟，维持原本相对音视频偏移。来源级偏移仍独立应用一次。内部缓冲和参数校验支持归一化后最多20000ms；不能将负值静默归零或退回默认音轨。新增正值、零、负值以及混合正负值的视听同步测试，验证实际时间关系和新增延迟。

输入选择使用明确映射将目录轨道标识转换成当前流的音频序号；禁止将视频占用的绝对索引直接套入 `a:N`。通过“视频索引0、音频索引1和2”的测试源验证两条音频不会串轨或越界。

## 4. 核验 GPU，再执行最终验收 / Verify GPU and complete acceptance

环境探测必须重新执行。`/dev/dxg` 只能证明 WSL GPU 接口存在；DISPLAY 或 WSLg 目录存在也不等于实际使用硬件渲染。必须记录 OBS 实际 renderer、实际编码器，以及浏览器实际解码统计。

本次只读检查实际返回 `DISPLAY=:0`、`WAYLAND_DISPLAY=wayland-0`，且 `/mnt/wslg` 与 `/dev/dxg` 存在。因此报告中“当前完全没有 WSLg 会话”不能直接沿用；下一步检查图形连接权限、库加载和实际 renderer。此次未执行图形渲染或性能测试。

优先验证 Windows Chrome 播放现有 WSL 后端；浏览器播放本身不必依赖 WSLg。OBS 的图形渲染环境和浏览器的执行环境分别排查。

对于 OBS NVENC 头文件缺失，先检查当前固定 OBS 版本依赖与现有构建方案；能够在用户缓存目录安装匹配的构建依赖时完成安装和增量构建，然后验证编码器确实注册并能发布。无法满足依赖时记录具体失败，不把“缺头文件”直接等同于 GPU 不可用。

按顺序执行：

1. 音频修复后完成自动化回归和短时真实媒体验证。
2. 五路 Direct/Hybrid 浏览器连续播放30分钟，测各路实际帧推进、首帧、重连和资源占用。
3. 五路 Composite 在原始1920×1080及原目标帧率下连续播放30分钟，同时采服务端与浏览器指标。若仅能运行降负载配置，单独报告，不能代替原规格通过。
4. 独立故障注入阶段断开并恢复一路，验证其余四路不中断、恢复后15秒内出图；用可控代理或测试路由模拟，避免修改真实摄像头或全机网络。

验收目标：首帧≤20秒；已就绪路由重开≤8秒；解码帧率≥配置目标90%；正常运行无超过3秒的非预期帧停滞；无崩溃及持续重连。记录 OBS 渲染/编码、网关转码和浏览器解码各自指标。CPU 610～720%应注明是多核累计口径。

旧的41帧/20秒约为2fps：它证明媒体持续推进，但不能满足5fps目标的90%门槛。低负载30分钟服务端发布也不能证明五个输入画面持续更新；使用逐源健康信息及浏览器帧证据共同判断。
