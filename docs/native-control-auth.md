# 原生控制认证边界 / Native control authorization boundary

## 当前交付与限制 / Delivered scope and limits

这是 renderer-free C++ 库、真实账号授权后端 adapter 与安全回归，不是已接入原生 OBS UI 的账号产品。没有新增 listener、登录入口、服务启动或 OBS 动作执行；不初始化第二媒体/显示引擎。Electron 兼容产品仍为默认入口。不能把库测试通过写成原生产品认证、旧数据迁移或 P3 已验收。

These renderer-free libraries provide persistent-session authorization and a bounded adapter to the existing account service, not a native login product. They start no service or listener, execute no OBS action and leave the compatibility Electron product as the default.

[NativeControlAuth](../core/include/webobs/native_control_auth.hpp) 直接复用 [SessionStore](../core/include/webobs/authentication.hpp) 的 SQLite 持久会话和令牌哈希。[NativeClusterAuthorizationBackend](../core/include/webobs/native_cluster_authorization.hpp) 实现其 fresh RBAC 回调；没有另造 session 协议、Basic 管理员回退或新账号服务。

## 固定命令与检查 / Allowlisted checks

- `read_scene` → `scene.read`；`write_scene` → `scene.write`；`view_camera` → `live.view`。最后一种必须带一个 camera ID；其余允许一个明确 scope。URL、路径、列表和通配符不能作为 camera scope。
- 在访问会话/账号后端前验证真实 socket/IPC 提供的 loopback peer、精确 Origin/authority、字段长度、命令和 scope。配置只接受明确的 loopback HTTP(S) origin，不接受 userinfo、路径、query、fragment、DNS 后缀或宽泛 localhost 子串匹配。
- SessionStore token 必须为 64 位小写十六进制。逐命令检查本地会话并调用最新账号授权，不缓存角色/许可；许可后再验证会话，拒绝后端请求期间发生的 logout。
- 缺失/失效/未绑定的旧会话 `401`（零后端请求）；账号不存在、禁用或身份/认证 epoch 不符时，成功撤销该 username/userId/authEpoch 的全部本地会话后 `401`，不误撤销同名重建或重新登录的新身份。撤销未确认删除记录则保守 `503`，包括数据库删除失败或并发已删除。权限不足 `403`；未配置、后端故障/异常或未知决定 `503`。许可后再检查 username 与完整绑定，拒绝进行中的 logout/身份替换。拒绝不返回 principal、异常详情或 token。

Each native command requires an explicitly bound username/userId/authEpoch session AND a fresh authoritative permission/scope decision. Legacy unbound sessions are rejected before backend I/O, never adopted by username. Revocation targets that exact binding; fresh same-name logins and recreated accounts are preserved. Allowed replies are followed by a complete local identity recheck. This is a decision-time check, not an execution-time fence or reusable grant.

## 真实账号后端 / Authoritative account backend

- 绑定身份调用的固定目标是 `http://127.0.0.1:<port>/auth/native-authorize`；三参数 legacy 诊断重载仍使用 `/auth/authorize`，原生会话 gate 不回退到该重载。默认端口 8095；配置只接受非零 uint16 端口、64 位小写 hex 内部凭据、connect 1–500 ms、total 1–2000 ms 且 connect≤total。未来配置 parser 必须在转换 uint16 前拒绝越界数，不能先截断。
- 绑定 POST 发送 `username`、`userId`、`authEpoch`、固定 permission、`cameraId`；legacy 诊断请求不含两个身份字段。**不传 groupId**：现有 cluster 会信任显式 groupId，省略后才按真实 camera registry 查询组。浏览器 cookie、session token 和 Basic 凭据不转发；内部 token 只用于 `X-WebObs-Internal-Admin`。
- 强制 loopback IPv4 HTTP、禁用环境代理、重定向、netrc 和 HTTP Basic；每次创建独立 easy handle，连接/总时限、4 KiB body、16 KiB 聚合 headers/128 次 header callback 均有界。C callback 捕获异常，错误不输出原始响应或秘密。
- 绑定响应只有严格 JSON（拒绝重复键、NUL、尾随数据）且 `200` 精确包含 `allowed:true`、与请求相等的 32 位小写 hex `userId` 和 `authEpoch`、请求 permission 回显共四字段，才许可；缺少 epoch 的 legacy 三字段响应不能用于绑定调用。仅精确识别 `403 permission_rejected` 与 `404 user_not_found` 及当前固定 message；错误内部 token、其他状态/结构或措辞变化一律 unavailable，而非默认许可或撤销账号。

The adapter uses the existing [cluster authorization route](../cluster/cluster_service.py), not a replacement service. It validates the full reply rather than trusting status 200. Strict error-message matching deliberately fails closed if the backend contract changes. Proxy/redirect traps and malformed replies are tested separately from the real Handler/ClusterStore/registry integration.

## 全操作授权编排 / Whole-operation authorization orchestration

[NativeOperationAuth](../core/include/webobs/native_operation_auth.hpp) `authorize_operation` 按声明顺序逐项查询权威后端（至多 16 项，permission≤32、resource≤128，拒绝重复对与控制字符）。每次同步调用前后检查统一经过时间预算；只有预算内返回的全部许可才产生 `allowed`。预算相等/耗尽、时钟异常/回退或无法表示的时间差返回 `unavailable`，优先于迟到的后端决定，并停止后续调用。`evaluated` 是及时许可前缀数，不是后端调用总数。非法输入、非正或无法用 steady clock 表示的预算返回 `invalid_request` 且零后端调用；及时的拒绝返回 `forbidden`，身份不符返回 `binding_invalid`，故障返回 `unavailable`。

它不读取或撤销本地会话，不检测 logout；`authEpoch` 是认证身份轮换守卫，不是 RBAC policy/registry revision。因此逐项 fresh RBAC 不构成整操作单一策略快照；最后权威检查之后的身份轮换也没有执行栅栏。同步 backend/clock 回调不能抢占，拒绝迟到结果不等于限制函数实际返回时间。宿主仍负责会话前后复查、可信 graph 身份/策略一致性以及执行序列化与硬截止；这些没有因本编排器而完成。未接入 listener、产品路径或 OBS 动作。

`authorize_operation` performs fresh lookups in declaration order and checks one elapsed-time budget before and after each synchronous call. Only timely allows covering every requirement yield `allowed`; `evaluated` counts that timely allowed prefix. Budget equality/exhaustion, clock failure/regression or an unrepresentable interval yields `unavailable`, taking precedence over late backend outcomes. Calls cannot be preempted: rejecting late results does not bound actual return time. This function does not read/revoke sessions or detect logout. Authentication epochs are not RBAC-policy/registry revisions, so sequential decisions do not establish one policy snapshot or an execution fence. Session revalidation, trusted graph identity, policy consistency and host deadlines remain integration work.

## 整批授权决策基础 / Whole-batch authorization foundation

`ClusterStore.native_authorize_batch` 是 cluster 内部整批决策基础：当前**没有注册任何 HTTP 路由**，网络调用不可达。请求必须精确携带 `username/userId/authEpoch/requirements`，requirements 为 1–16 个 `{permission,cameraId}`；permission 只接受既有 allowlist，cameraId 只接受现有标识符语法或空 scope，重复对拒绝；全部字段、界限与去重校验在读取任何数据库之前完成。身份（username/userId/authEpoch）在同一 `BEGIN IMMEDIATE` cluster 快照内只校验一次，角色/scopes 的 principal 也只解析一次并用于整批；任一项拒绝即整批 `403 permission_rejected`，不返回可执行子集；身份不符沿用统一 `404 user_not_found` 并审计 `user-unknown`，本地会话撤销仍由原生 gate 负责。相机项的组元数据来自一个独立只读 Registry 连接、一次 `SELECT` 的单一快照：行缺失、组损坏、库缺失或查询失败使整批 `503 native_registry_unavailable`，不会像单条 `_camera_group` 那样退化为空组路径。cluster RBAC 与 Registry 是两个各自稳定的快照，没有共同线性化点；组改变与角色改变仍可能跨快照撕裂。这仍是决定时快照，不是执行栅栏，也未接入 listener、产品路径、UI 或媒体动作。

The batch helper validates the entire request before any database read, binds one identity check and one principal read inside a single `BEGIN IMMEDIATE` cluster snapshot, and denies the whole batch when any item denies — no partially executable subset is returned. Camera-bound items resolve groups from one dedicated read-only Registry snapshot; a missing row, corrupt group, absent database or failed query fails the whole batch closed as `native_registry_unavailable` instead of degrading to the empty-group path. Cluster RBAC and Registry are two independently stable snapshots with no common linearization point, and this remains a decision-time snapshot, not an execution fence or a routed endpoint.

## 接入前仍须保留的契约 / Remaining integration contracts

可信 adapter 必须从 socket 获得 peer，不信任 `X-Forwarded-For` 或请求 principal；在构造请求前拒绝重复/折叠的 Host、Origin、cookie，限制 body/header、连接数与请求时限。当前库不是 HTTP parser，也不验证 OBS 参数。会话及内部凭据文件仍须 owner 私密目录/Windows ACL；账号服务仍须受单实例、Job 与退出回收管理。仅通过授权后在同一原生 frontend 线程操作同一 OBS graph；不开放旧 core 通用可写 API，不启动完整 Supervisor。

库只检查声明的单个 scope，不能解析整场景。可信执行 adapter 必须从实际目标推导所有受影响 camera ID 并逐个授权，对读取结果做可见性过滤。无 scope 的 `scene.read/write` 是粗粒度权限，**不是所有相机范围的豁免**；现有 cluster 的管理员/显式 scope 许可也不是 camera 对象存在性证明，执行前须解析目标。

原生菜单/快捷键/dock/脚本等修改入口必须界定和防绕过。`authorize` 后应立即执行对应白名单动作；最后检查之后发生撤销的处理仍须执行序列化策略定义。SessionStore 与 NativeControlAuth 已实现完整 username/userId/authEpoch 绑定及许可后复查；旧 HTTP/Electron 协议没有因此改成原生绑定协议。整操作编排器没有本地会话输入，尚须宿主把会话生命周期与多资源检查、策略一致性和执行序列化正确连接。

The libraries do not implement native login, graph-derived multi-camera authorization, UI bypass controls, private ACL provisioning, account-service ownership or reversible migration. Immutable user/session authentication bindings are implemented in the native gate; whole-operation session wiring, atomic policy consistency and execution fencing remain unresolved integration issues. libcurl ownership is balanced; concurrent invocation assumes normal C++ object lifetime and a supported modern libcurl build with thread-safe global initialization. Destruction/mutation concurrent with a call is not supported.

## 独立验证 / Standalone validation

需要 C++20、OpenSSL Crypto、SQLite、libcurl、Jansson、Python 3 和 Threads；不配置 libobs/Qt/GStreamer，不启动媒体进程：

```sh
cmake -S native-host/tests/control-auth -B build/native-control-auth -DCMAKE_BUILD_TYPE=Release
cmake --build build/native-control-auth --parallel 2
ctest --test-dir build/native-control-auth --output-on-failure
```

测试使用临时 SessionStore、真实 cluster Handler/ClusterStore 和合成 camera registry，密码 hasher 为 fixture（不测试 Argon2/登录）。覆盖同会话角色/直接相机 scope 改变、registry 组改变、禁用账号撤销全部本地会话、错误内部凭据 503 后恢复；独立 hostile HTTP 覆盖状态与 JSON 不符、重复键、控制字符、超限、超时、无代理/重定向泄漏。无效 direct 请求用活跃 observer 断言零网络请求；probe 每次响应有独立时限，CTest 另有整体时限。原会话库的 expiry/logout/SQLite 删除失败等回归继续运行。

The standalone and root CTest projects exercise the actual account-service implementation against disposable data, not a production profile. Non-MSVC builds scan both static libraries for forbidden media/frontend symbols. CI builds on Linux and MSVC using the existing pinned vcpkg baseline and a [minimal test manifest](../native-host/tests/control-auth-vcpkg/vcpkg.json) with OpenSSL/SQLite/curl/Jansson. These are test dependencies, not added shipped services or native installer components. Passing them is not Windows ACL, native UI, camera, pixel or performance qualification.

## 只读 graph 观察基础 / Read-only graph observation

独立的 [wall snapshot](../native-host/src/wall_snapshot.hpp) 现在可观察现有、无 filter 的平面五项 Media Source scene；它只复制 scene/source UUID、item ID 与用户可见标记，包含隐藏项和重复 source。不读 settings/名称/URL，不创建、删除、选择、保存或启动媒体。源码只进入独立 API 契约测试，不接入产品插件或认证库，不暴露管理路由。固定 OBS headers + 15 个只读/引用/加锁替身在本地覆盖 84 情形，包括失败清空、引用平衡、异常不穿越 C callback、第六项及禁用 filter 拒绝。

这只是后续身份解析所需的观测，不是全依赖图、可信绑定或授权预检：不包含 transforms/audio/show-hide transitions，不证明 source settings 或 collection incarnation 未改变。必须由正确 frontend/control context 的调用者序列化 collection/source/filter 编辑；scene lock 不是全图锁，filter 遍历和锁等待无硬时限。未来私密 owner map 不能由请求字段、URL/名称相等或相同 UUID 元组替代；先对每项解析真实对象及可信 camera/profile 身份，再做去重和全 scope 检查。

The internal inspector is now implemented and locally tested, but remains entirely unexposed. Its owned UUID/item/visibility DTO is only an observation: it neither proves authoritative camera/profile identity nor covers transitions, source settings, audio or future graph use. No hard whole-operation deadline is implied. Sequential single-item RBAC calls can still span different policy epochs despite the implemented immutable native user/authentication-epoch binding; the unexposed whole-batch helper closes that cluster-side gap by deciding every requirement from one RBAC snapshot, while the Registry group snapshot remains independent and UI bypass prevention, private service ownership and authorized reversible apply still require separate implementation before any live action.

## 可信 graph 身份基础 / Trusted graph identity foundation

`native-host/src/source_ownership.{hpp,cpp}` 是未接入产品的本地来源（provenance）基础：账本只记录**由 native host 自己创建**的源——camera_id 来自创建时的私有 product 配置，source_uuid 读取自新建 obs_source。复用同名/同设置的既有源不构成来源证据，绝不写入；名字、URL 与设置被刻意排除，因此无法被用于冒领身份（ABA）。严格 JSON（schema 1，至多 16 条，camera_id 镜像 cluster IDENTIFIER 语法，canonical 小写 UUID，generation 唯一递增）任何偏离一律 fail-closed：解码损坏或自相矛盾（重复 uuid、重复 camera_id、重复 generation）时分类结果全部 unbound。同一 camera 记录新 incarnation 会替换并释放旧 uuid（旧 uuid 此后 unbound）；uuid 被另一 camera 占用则 record_conflict 且不留痕。分类只做精确 UUID 相等：账本条目不是授权 grant，不绑定会话/账号/RBAC scope，也不证明源仍存活或仍是媒体——决策时必须与新的 snapshot 配对，TOCTOU 窗口仍然存在。持久化现已在 plugin **仅创建成功路径**接线：`native-host/src/ownership_store.{hpp,cpp}` 做有界写入（至多 16 KiB；POSIX 0600；Windows 文件继承父目录 ACL，不做 private_stage 式句柄 DACL 验证）加重命名，写入前先解码回读、损坏或自相矛盾账本在任何写入前拒绝。不做 fsync/FlushFileBuffers，不声明断电原子性（Windows remove-before-rename 崩溃窗口为已知边界）。账本 codec 模块本身仍无文件/网络/OBS API；plugin 只登记本次尝试新建（created_here）的槽位，账本失败仅写入 receipt 的 `ownershipLedger` 标记而不改变 wall 结果；分类、授权、预览与投影路径仍不消费来源证据（构建契约禁止 plugin 出现 classify/authorize 符号）。决策时配对已落地为未接入的 `native-host/src/wall_live_decision.{hpp,cpp}`：先把 snapshot UUID 严格校验（语法+去重，违反即 invalid_request），再要求账本自洽（违反即 ledger_invalid），每条 snapshot 条目必须精确匹配账本 UUID（任一 unbound 即 graph_unbound），三种失败均零次调用注入的授权回调；随后按 snapshot 顺序逐个授权，首个 denied 即 forbidden、首个 unavailable（含回调抛异常）即 unavailable，均立即停止并只记录已接受前缀，迟到 allow 一律忽略。这是决策时快照，不是 grant、不是可复用能力、不是执行栅栏；不证明媒体持续存活或 graph 未变，调用方仍须在决策时提供新 snapshot，TOCTOU 窗口在本模块之外。plugin 不链接也不调用该模块（构建契约锁定）。UI 旁路防护、可逆 apply 与目标机验证仍待完成。

`native-host/src/source_ownership.{hpp,cpp}` is an unwired local provenance foundation. The ledger records only sources created by this native host itself: camera_id comes from the private product config at creation time and source_uuid is read from the newly created obs_source. Reusing an existing same-name/same-settings source is not provenance and is never recorded; names, URLs and settings are deliberately excluded so they cannot be used to adopt an identity (ABA). Strict JSON (schema 1, at most 16 entries, camera_id mirroring the cluster IDENTIFIER syntax, canonical lowercase UUID, unique increasing generations) fails closed on any deviation: a corrupt or self-contradictory ledger (duplicate uuid, duplicate camera_id, duplicate generation) yields fully unbound classification. Recording a new incarnation for the same camera replaces and frees the previous uuid (which becomes unbound afterwards); a uuid claimed by another camera is a record_conflict leaving no trace. Classification performs exact UUID equality only: a ledger entry is not an authorization grant, does not bind a session/account/RBAC scope, and does not prove the source is still live media — it must be paired with a fresh snapshot at decision time, and the TOCTOU window remains. Creation-time persistence is now wired on the plugin's successful bootstrap path only: `native-host/src/ownership_store.{hpp,cpp}` performs a bounded write (at most 16 KiB; POSIX mode 0600; on Windows the file inherits its parent directory ACL without private_stage-style handle-DACL verification) plus a temp-file rename, re-decoding the ledger and refusing corrupt or self-contradictory content before any write. It does not fsync/FlushFileBuffers and claims no power-failure atomicity (the Windows remove-before-rename crash window is a documented limit). The plugin records only slots created by this attempt (created_here); a ledger failure only marks the receipt (`ownershipLedger`) and never changes the wall outcome. The codec module itself still touches no file, network or OBS API, and no classification, authorization, preview or projector path consumes provenance yet (the build contract forbids classify/authorize symbols inside plugin.cpp). Decision-time pairing now exists as the unwired `native-host/src/wall_live_decision.{hpp,cpp}`: snapshot UUIDs are validated first (syntax plus duplicate-free, violations yield `invalid_request`), then the ledger must pass the shared fail-closed consistency rules (`ledger_invalid`), every snapshot entry must match a ledger UUID exactly (any unbound entry yields `graph_unbound`), and all three failure classes call the injected authorizer zero times; only then does the authorizer run in snapshot order, where the first `denied` yields `forbidden` and the first `unavailable` (including a thrown authorizer) yields `unavailable`, both stopping immediately and recording only the accepted prefix, with late allows ignored. This is a decision-time snapshot, not a grant, not a reusable capability and not an execution fence: it proves no continued media liveness or an unchanged graph, callers must still supply a fresh snapshot at decision time, and the TOCTOU window stays outside the module. The plugin neither links nor calls the module (locked by the build contract). UI-bypass guards, reversible apply and target-machine verification remain open.

## 实时预览决策管线 / Live-view decision pipeline

## 授权应用执行器 / Authorized-apply executor

`native-host/src/wall_apply_executor.cpp` 是未接入产品的执行边界：它只消费 `authorize_wall_apply` 产出的计划，不重新判定权限，也不接触 OBS。执行分两段：先用**新鲜快照**和**当前账本**以 `plan_wall_apply` 重算计划（期望状态由计划本身的操作推出），传入计划必须与重算结果逐字段一致，否则返回 `stale_plan` 且目标回调一次都不执行；随后按计划顺序执行 replace/remove/add，keep 绝不触碰目标。首个前向操作失败时，按逆序回放已执行前缀的日志，即使某条撤销失败也会继续尝试全部条目，并据实返回 `operation_failed_rolled_back` 或 `operation_failed_rollback_incomplete`。

边界保持不变：重算只收窄“观察—执行”窗口，不构成全局原子、执行栅栏或可复用凭证；回滚只能恢复账本/图声明，无法重建被删除的源对象及其设置；没有持久化、崩溃恢复或跨步骤原子性承诺。该模块与插件解耦，构建契约锁定它不得被产品插件链接或调用。

The uncovered execution boundary lives in `native-host/src/wall_apply_executor.cpp`. It consumes only a plan produced by `authorize_wall_apply`; it never re-decides permissions and never touches OBS. Execution has two phases: first the plan is recomputed with `plan_wall_apply` from a **fresh snapshot** and the **current ledger**, using the desired state implied by the plan's own operations; the passed plan must match that recomputation field for field, otherwise the result is `stale_plan` and no target callback runs. Then replace/remove/add operations run in plan order while keep operations never touch the target. On the first forward failure the journal of the applied prefix is replayed newest-first; every undo entry is attempted even after a failure, and the status honestly reports `operation_failed_rolled_back` or `operation_failed_rollback_incomplete`.

The boundaries stay unchanged: re-derivation only narrows the observation-to-execution window; it is not global atomicity, an execution fence or a reusable capability. Rollback restores ledger/graph claims only and cannot recreate deleted source objects or their settings. No persistence, crash-recovery or cross-step atomicity is claimed. The module stays decoupled from the plugin, and the build contract locks that the product plugin never links or calls it.

## 授权应用备份捕获 / Authorized-apply backup capture

`native-host/src/wall_apply_backup.cpp` 补齐执行器的可逆性缺口：在执行任何 replace/remove 之前，通过注入的读取器捕获被销毁源的**有界不透明设置**（单源 ≤64 KiB，总量 ≤512 KiB）；缺失、抛异常或超限一律整体 `unavailable`，绝不保留半份材料，执行器因此不应启动。捕获按计划顺序进行，同一旧 UUID 只允许出现一次。失败后由注入的写入器按“最新优先”回放恢复，逐条尝试并如实返回 `restored/failed/complete` 计数。

边界：捕获与恢复都不做授权、不读 OBS/文件/网络、不是执行栅栏；设置材料只是 best-effort 恢复证据，不承诺持久化、原子性或崩溃恢复；产品插件不得链接或调用（构建契约锁定）。

The executor's reversibility gap is closed by `native-host/src/wall_apply_backup.cpp`: before any replace/remove, an injected reader captures the **bounded opaque settings** of the source being destroyed (≤64 KiB per source, ≤512 KiB total). A missing blob, a thrown exception or an oversize blob makes the whole capture `unavailable` with no partial material, so the executor must not start. Capture follows plan order and each old UUID may appear only once. After a failure an injected writer replays the material newest-first, attempts every entry and reports honest `restored/failed/complete` counts.

Boundaries: capture and restore never authorize, never read OBS/files/network and are not an execution fence; the material is best-effort recovery evidence with no durability, atomicity or crash-recovery promise, and the product plugin must not link or call the module (locked by the build contract).

## 备份感知执行组合 / Backup-aware execution composition

## 普通启动拒绝与诊断分离 / Ordinary startup refusal and diagnostic separation

`startup_bootstrap` 把 FINISHED_LOADING 中的插件升级快照、`product.json`/`wall.json` 读取、视频配置、来源创建、场景选择及所有权写入封在同一个回调内。普通启动无操作员会话，回调零次；纯 C++ 可执行回归覆盖上下文组合、调用次序和异常，并以无条件调用替身做负控制（预期失败）。显式 `-DiagnosticBootstrap` 只允许短期 SmokeToken/CrashProbe；启动器清除继承的诊断/像素/重启选择器，仅为显式请求设置诊断值和运行目录。插件核对固定 OBS pin、非默认原型 manifest、portable sentinel 和模块配置路径。测试开关、令牌、环境变量和这些路径核对均不是 RBAC 或私密文件安全边界。

Windows 新建隔离夹具在显式诊断之前分别放置产品配置（含不同 canvas）和 wall fallback，实际启动同一插件、不给诊断参数，检查拒绝回执、前后实际视频一致且 ffmpeg 来源为零，以及没有插件引导/账本文件和升级快照。此后显式诊断仍验证新建/复用、硬解请求和实际视频；跨版本旧包的首次 smoke 使用固定提交的旧脚本，升级后仍用当前严格检查，不自动降级要求。

行为变化：普通启动不再自动做插件升级快照；快照仅保留于显式诊断回调。OBS 自己在 FINISHED_LOADING 之前的场景/来源恢复和原生编辑仍是缺口；刷新/投影已在插件内失败关闭，但这不等于完整 UI 门控、登录前无媒体、授权导入、全局原子性或迁移完成。短诊断启动器也不是长时 P5 采样入口。

The startup dispatcher encloses plugin upgrade snapshots, product/wall parsing, video configuration, source creation, scene selection and ownership writes in one callback. Ordinary startup has no operator session and invokes it zero times. Executable C++ tests cover context combinations, order and exceptions; an unconditional-callback negative control must fail. Only explicit short SmokeToken/CrashProbe launches may request DiagnosticBootstrap. The launcher removes inherited diagnostic/pixel/restart selectors; the plugin checks the pinned, non-default portable prototype and module paths. None of these checks or environment selectors are RBAC or a private-file security boundary.

The fresh Windows fixture starts the actual plugin without diagnostic permission for both product-with-canvas and wall-fallback cases before testing explicit diagnostics. It requires unchanged observed video, zero ffmpeg sources, no bootstrap/ownership outputs and no plugin snapshot. Old pre-upgrade binaries use a frozen compatible helper only for their first smoke; upgraded binaries keep the current strict gate. Ordinary starts no longer take plugin upgrade snapshots; explicit diagnostics retain that behavior. OBS's own earlier restore and native editing remain outside this fix; the plugin viewing entries now fail closed, but that is not a complete UI boundary or pre-login isolation. This is not pre-login media isolation, authorized migration, atomicity, a completed UI boundary or a long-duration P5 launcher.

## 只读绑定观察回执 / Read-only binding inspection receipt

诊断引导完成后，插件只对刚创建或复用的 wall scene 做一次只读快照（`inspect_existing_wall`），把五个 item 的 source UUID 与私有创建账本逐项精确配对，并仅在 `product-bootstrap.json` 写入计数：`bindingInspection=observed`、`bindingItems`、`bindingBound`、`bindingUnbound`。它不读取名称/URL/设置，不选择、创建、删除或保存对象，不启动媒体，也不调用授权后端；快照失败或账本损坏时只写入固定状态串。

边界：`bindingBound` 只是本地来源声明计数，不是 registry 身份、RBAC 授权、媒体存活或 graph 未变证明；复用同名/同设置的既有源不会被账本认领，保持 unbound；跨进程复用若账本持久化成功则仍为 5 bound，这只证明账本可被重新读取，不证明登录前隔离或授权。构建契约由“插件不得出现分类符号”改为“恰好一处 `classify_wall_entries`，位于该只读回执函数内，且函数体无任何改图或持久化调用”；插件仍不链接 `wall_live_decision`、`live_view_pipeline` 或授权路径。真实 OBS graph 回执由 Windows CI [42631296022](https://github.com/LiaoYK001/Web-Camera-Monitor-Wall/actions/runs/42631296022) 记录：fresh 与跨进程复用均为 `productBindingBound=5`、`productBindingBoundSecond=5`，见执行记录。

After the diagnostic bootstrap, the plugin takes one read-only snapshot of the wall scene it just created or reused (`inspect_existing_wall`), pairs the five item source UUIDs against the private creation ledger by exact equality, and writes counts only into `product-bootstrap.json`: `bindingInspection=observed`, `bindingItems`, `bindingBound`, `bindingUnbound`. It reads no names, URLs or settings, selects/creates/removes/saves nothing, starts no media and calls no authorization backend; snapshot or ledger failures write a fixed status string instead.

The boundary: `bindingBound` is a local provenance claim count, not registry identity, RBAC authorization, media liveness or an unchanged graph. Reused same-name/same-settings sources are never adopted and stay unbound; a cross-process reuse with a persisted ledger still reports five bound, which proves only that the ledger can be re-read, not pre-login isolation or authorization. The build contract changed from banning all classification symbols in the plugin to allowing exactly one `classify_wall_entries` inside that read-only receipt function, whose body must contain no graph-mutating or persistence call. The plugin still neither links nor calls `wall_live_decision`, `live_view_pipeline` or any authorization path. Windows CI [42631296022](https://github.com/LiaoYK001/Web-Camera-Monitor-Wall/actions/runs/42631296022) records the real-OBS receipts: fresh creation and cross-process reuse both report `productBindingBound=5` and `productBindingBoundSecond=5`; see the execution record.

### OBS 恢复图的可执行测量 / Executable measurement of the OBS-restored graph
