## 4. 目标架构

优先方案：固定版本的 OBS 原生前端作为 Windows 宿主，通过产品自己的插件、原生界面扩展和构建集成提供监控墙能力。

```text
摄像机原始 RTSP
      ↓
OBS 媒体源 / obs-ffmpeg
      ↓
OBS 支持的硬件解码与软件回退
      ↓
libobs 场景 / D3D11 渲染
      ↓
OBS 原生预览 / 投影窗口

Qt 原生产品界面 → 操作来源、场景、布局和配置
录像 / 远程分发 / 检测 / 网站来源 → 按功能需求接入
```

实施要求：

- 直接复用 OBS 的来源、场景、预览、投影和生命周期实现，减少自制同类实现。
- 本地普通 RTSP 监看直接进入 OBS 媒体源，避免必经 WebRTC、浏览器兼容转码及浏览器再次解码。
- 相同来源及兼容配置在多个场景、预览或投影中复用一个 OBS source；按来源、音轨、过滤器、配置和权限确定能否共享，不能只按 URL 粗暴合并。
- 本地监看不启动无关的视频编码器。多个投影可以增加必要绘制，但不能无故重复建立解码器。
- 初步方向为同一 GPU 完成解码和渲染，减少跨显卡复制；实际方案以同机测试为准。
- 记录实际适配器标识和逐路解码结果。`auto`、D3D11 存在或高性能 GPU 提示均不等于硬解已证实。
- 保留逐编码/逐设备的软件回退，明确记录原因及影响。
- 正常监看、录像和远程分发分别管理需求，确保退出一个观看端不会停止其他实际工作。

## 6. 阶段 P1：定位黑屏与补齐实际画面测试

按下面顺序定位，不跳过基础显示验证：

| 层级 | 操作 | 验证目的 |
| --- | --- | --- |
| A | 在原生窗口直接绘制已知颜色测试图 | 窗口、交换链、基础绘图状态 |
| B | OBS 场景加入色块、文字和位置标记 | 场景绑定、画布、Program 输出和纹理 |
| C | 播放本地动态 H.264、H.265 测试片 | 解码、视频纹理、颜色和持续呈现 |
| D | 单路真实 RTSP | 连接、认证、传输与编码兼容性 |
| E | 完整五路及实际布局 | 来源共享、布局和负载 |
| F | TAKE、重开、全屏、DPI、多显示器、断流恢复 | 状态同步与生命周期 |

逐项检查：

- 浏览器临时布局、已保存场景、Studio Preview 和已 TAKE Program 的关系。
- 原生显示绑定的输出通道和当前 Program 是否一致。
- 场景/source 的 active、showing、生命周期和线程归属。
- 各来源是否持续产生有效视频帧，场景是否实际渲染到主纹理。
- 交换链、视口、投影、矩阵、混合和色彩状态是否与对应 OBS 实现匹配。
- 实际渲染与解码适配器标识，是否出现跨设备复制或资源不兼容。
- 无录像、无推流时，原生预览是否独立正常工作。

测试要求：

- 测试片包含五路可区分的路号、颜色、空间标记和递增时间标记。
- 验证最终显示区域的像素内容和持续变化，不只检查来源尺寸、健康状态或绘制次数。
- 能区分黑屏、旧帧、错误来源、缺一路及错误布局。
- 黑色是合法画面内容，不能用任意摄像机画面“亮度必须大于阈值”作为通用健康判断。
- CI 验证已知图案与渲染输出；实际 Windows 桌面窗口、物理 GPU 和真实摄像机另做实机验证。
- 截图、像素读回和帧分析仅用于测试或短时诊断，不能在生产模式逐帧读回 CPU。
- 修复后保留一个能捕获原缺陷的回归测试。

通过条件：有明确根因和证据，五路最终画面持续正确；不能以启动持续编码/虚假录像作为预览工作条件。

建立功能迁移表：每项现有能力标明“已迁入原生宿主、按需组件、远程后端提供、待迁移”。不得静默丢弃用户功能。

## 10. 阶段 P5：同机性能验收

### 固定测试条件

- 同一台 13900HX / RTX 4090 Laptop，记录 Windows、驱动、电源及散热状态。
- 同样五路输入，保持分辨率、帧率、码率、音频和 RTSP 传输方式一致。
- 相同画布、显示尺寸、DPI、显示器、可见窗口数量与布局。
- 使用可比 GPU 和解码设置，记录适配器标识；不能比较两块不同显卡的百分比后直接下结论。
- 本地预览基线中，两侧均关闭录像、推流、检测等额外工作；额外功能另建对照场景。
- OBS 与产品交替单独运行，避免同时占用解码器和改变摄像机负载。
- 合成来源服务器放在外部或保持两侧完全一致，不将仅一侧拥有的 fixture 发布器排除后作不公平比较。

### 采样方法

- 每次预热至少 3 分钟，正式采样至少 20 分钟。
- 至少三组成对测试，交替先后顺序，记录温度和频率状态。
- 每轮给出中位数/平均值、p95、峰值以及测量误差说明。
- 初步达标后进行至少 2 小时稳定性测试，覆盖重连、窗口与场景切换。

### 必须报告的指标

| 指标 | 要求 |
| --- | --- |
| CPU | 全部所属进程累计 CPU 时间、平均值和 p95，含辅助服务 |
| GPU | 分适配器、分 Video Decode / 3D / Copy 等引擎，方法一致 |
| 内存 | 全进程范围，平均、峰值、持续增长，说明共享内存计量方式 |
| 显存 | 对应设备上的平均、峰值与异常增长 |
| 实际画面 | 每路有效帧进度、冻结、丢帧、异常黑屏与布局正确性 |
| 延迟 | 用同一方法测量端到端延迟，保留统计分布 |
| 功耗 | 可获得的整机/设备功耗，同条件记录 |
| 后台工作 | 来源连接、解码器、转码任务、编码器和完整进程清单 |
| 体积 | 安装器、默认安装、实际扩展安装的文件字节数 |

必要时使用 ETW/WPA、GPUView、合适的呈现分析工具定位。工具开销在两侧保持一致；正式性能结果应包含低干扰采样。

不得直接相加口径不同的任务管理器 GPU 百分比，不得重复计算父子进程或共享 GPU 时间。产品主进程变轻、后代或系统合成器变重时，需要报告整体影响。

### 判定原则

- 每个主要指标给出 `产品值 / OBS 值` 和原始数据位置。
- CPU 与可比 GPU 工作成本的目标为不高于 OBS。
- 内存、显存、功耗和延迟必须一起审查；有回退时不能笼统宣布“整体开销小于等于 OBS”。
- 差异落在测量不确定范围时继续采样，记录不确定性，不能选择一次低读数作为达标证据。
- 黑屏、漏路、降分辨率、降帧、静音、隐藏窗口暂停、额外延迟或关闭另一侧仍启用的功能，均不能用于达标。
- 合成小流、CI、配置 `auto` 和窗口 draw callback 只提供对应层面的证据，不能替代实际目标机器的五路验收。

```text
保存复现与基线
    → 选择当前最大的可测缺陷/开销
    → 定位原因并完成一项可验证修改
    → 执行相关单元/集成/安全/安装检查
    → 执行 Windows 同条件 OBS 对照
    → 记录结果、剩余问题与下一轮假设
    → 交付开发候选供目标机器复验
    → 未达标则继续下一轮
```

验证按实际变更选择并维护：

- C++ 构建、CTest、原生渲染和媒体测试。
- Windows 真实入口、窗口、来源、场景/TAKE、退出与崩溃清理测试。
- 认证、Origin、权限、私有配置及代理边界的相关回归。
- 前端仍存在或受到影响时执行相应 typecheck/build/重点 Playwright 套件。
- Windows 实际打包、隔离安装/升级/卸载和数据保留验证。
- 原有 Electron 专属测试在组件迁出后由新宿主的等价行为测试接替；不能仅删除测试后声称通过。
- 检查依赖审计、许可证、源码身份和安装包完整性。

Windows 开发候选通过 GitHub Releases 的 **Pre-release** 提供直接下载，附摘要、变更、已测范围、已知问题和原生入口说明。用户已表达 Releases 下载优先，避免仅提供 Actions Artifacts。

开发包使用 `-dev.*` 身份，不能进入稳定更新源或提升稳定 Latest。稳定发布仍是独立流程，不由本计划自动授权。
